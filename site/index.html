How I built this

A git push is the only way this site changes: GitHub Actions logs in to AWS with a short-lived token, Terraform plans and applies the infrastructure, and the pipeline publishes the files.

Build sequence

  1. 1

    Bootstrap

    Run once from my PC

    Terraform creates an encrypted, versioned S3 bucket for Terraform state, a GitHub OIDC identity provider, and a deploy role GitHub Actions can assume. The role trusts only this repository, identified by GitHub's permanent numeric owner and repo IDs, so a renamed or recreated repo cannot use it.

  2. 2

    Pipeline

    Every push

    Format check, validate, security scan and plan run on every push. Pushes to main also apply and publish. Pull requests stop at plan, so a proposed change is reviewed before it touches AWS.

  3. 3

    Hosting

    S3 + CloudFront + ACM

    A private S3 bucket readable only by CloudFront through Origin Access Control. HTTPS enforced. A free ACM certificate for aws.jakemoore.dev, validated by DNS and renewing automatically.

  4. 4

    Serverless

    Lambda + DynamoDB

    A Python Lambda function sits behind CloudFront at /api. A DynamoDB table holds the visitor counter and the uptime history.

  5. 5

    Operations

    EventBridge + CloudWatch + SNS

    EventBridge runs the uptime check every 30 minutes. CloudWatch alarms send email through SNS. A nightly job checks for drift.

Terms used on this page

Terraform
Code that declares cloud resources; it computes and applies the difference.
OIDC
A sign-in standard that lets GitHub prove its identity to AWS without a password.
S3
File storage; holds the site's HTML, CSS and JavaScript.
CloudFront
Content delivery network; serves the site over HTTPS from edge locations.
ACM
Certificate Manager; issues and renews the TLS certificate.
Lambda
Runs a function on request, with no server to manage.
DynamoDB
Serverless key-value database.
EventBridge
Scheduler that triggers a function on a timer.
CloudWatch
Metrics, logs and alarms.
SNS
Notification service; delivers alarm emails.

How this updates

  1. A push to main runs the pipeline.
  2. Terraform applies the change and counts the resources it manages.
  3. The pipeline writes /status/deploy.json with the commit, run and scan results.
  4. This page reads that file, so the figures above always describe the build that is live.

Security

Each control is defined in the Terraform code and checked on every push.

ControlHowWhere in AWS
No stored cloud keysGitHub Actions receives a short-lived token through OIDC for each run. No access key exists to leak.IAM OIDC identity provider
Least-privilege deploy roleScoped by name to this project's buckets, function and table. It can create only roles prefixed iac-portfolio-app-, so it cannot raise its own permissions.IAM role and policy
Private storageS3 public access fully blocked. Only this CloudFront distribution can read the bucket.S3 bucket policy, CloudFront Origin Access Control
HTTPS onlyHTTP redirects to HTTPS. TLS 1.2 or higher. HSTS tells browsers to use HTTPS every time.CloudFront viewer policy, ACM

Alerts

CloudWatch alarms watch two signals: the site failing its uptime check, and errors in the Lambda function. Either one sends an email through SNS.

Drift check

First nightly check not available yet.

Drift means AWS was changed outside the code. Each night a job runs terraform plan against the live account and would flag any difference.

Change process

  1. Git commit
  2. Plan, reviewed in the pipeline
  3. Apply

Nothing is changed by hand in the AWS console.
